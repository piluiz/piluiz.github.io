Out-of-Order RISC-V Processor

fall 2025 · uiuc ece 411 · #systemverilog #risc-v #computer-architecture

For UIUC's ECE 411 (Computer Organization & Design), my team designed a 2-way superscalar, out-of-order RISC-V processor in SystemVerilog over eight weeks. I worked across most of the core, and built the Gshare branch predictor and most of the load-store queue.

Overview

Our core implements the full RV32IM instruction set, including multiply and divide. It executes instructions out of order to avoid stalls and keep the execution units busy, while still committing them in program order so exceptions stay precise.

It uses explicit register renaming with a reorder buffer (ROB) to track in-flight instructions, and reservation stations that let instructions wait for their operands without holding up the rest of the pipeline. Here’s a simplified look at how instructions finish out of order but commit in order:

Design


I was involved in most phases of the core. ✦ highlighted = parts I led.


Core


    

  • 2-way superscalar: fetches, decodes, dispatches, and retires up to two instructions per cycle
    • 

  • Explicit register renaming with a reorder buffer for in-order commit and precise exceptions
    • 

  • Reservation stations so instructions wait for operands without stalling the pipeline
    • 



Front end


    

  • Gshare branch predictor that hashes global branch history with the branch address
    • 

  • Next-line prefetching for sequential instruction fetches
    • 



[ gshare.gif ]
A loop branch goes taken, taken, taken, then not taken to exit. Gshare keeps a counter for each recent history, so it can learn that after T T T comes the exit. (In hardware, the counter is picked by PC xor history.)


Memory


    

  • Pipelined instruction and data caches (split L1 I-cache and D-cache), sharing memory through a bus arbiter
    • 

  • Split load-store queue so loads and stores schedule independently while keeping memory order correct
    • 





Every feature was a trade-off between performance (IPC), power, area, and timing. Going 2-wide superscalar is a good example: it didn’t buy us much performance, but we wanted to learn how to build one, so we did it anyway, knowing it wasn’t the most efficient choice.




Tools and verification


Every instruction the core commits is checked against Spike, the official RISC-V reference simulator. If the PC, registers, or memory ever differ, the testbench flags a mismatch, which is what makes it possible to debug a core that runs instructions out of order.


[ flow ]
simulate
 C / asm ──[ RISC-V GCC ]──▶ program
 RTL + program ──[ VCS / Verilator ]──▶ IPC · cycles · branch accuracy
                 └──▶ every commit checked against Spike

lint
 RTL ──[ SpyGlass ]──▶ lint clean

synthesize
 RTL ──[ Design Compiler + OpenRAM ]──▶ timing · area
 + switching activity from sim ───────▶ power
every stage runs on the same RTL


    

  • Simulation: Synopsys VCS as the main simulator, Verilator as a free alternative, and Verdi for waveforms
    • 

  • Programs: RISC-V GCC builds the test programs, including CoreMark, which reports IPC, cycles, and branch accuracy
    • 

  • Lint: SpyGlass, which has to come back clean
    • 

  • Synthesis: Design Compiler maps the RTL to gates and reports timing and area, with OpenRAM generating the SRAMs and DesignWare providing the multiplier and divider
    • 

  • Power: switching activity from simulation is fed back into Design Compiler to estimate power
    • 



Takeaways


This project was a struggle. We were in a constant time crunch, and debugging an out-of-order core was tedious. The class ended with a design competition, and our core didn’t even make the leaderboard: it deadlocked on some of the tests because of a superscalar bug where one of the two ways could accidentally drop an instruction.


It wasn’t the result we wanted, but it pushed me to grow a lot as an RTL engineer. My stronger suit had always been C++, and I didn’t always have a clear picture of how my RTL would synthesize into gates. Building that intuition was one of the coolest parts of the project. Plenty of my habits didn’t translate to hardware at first: for example, I reset every flip-flop on a pipeline flush, when clearing a valid bit and clock-gating the rest would have done the same job for much less power. RTL is also much slower to iterate on than software, which makes every bug more expensive.
